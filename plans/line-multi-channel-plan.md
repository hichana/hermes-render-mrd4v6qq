## Goal

Let each client agent within one business's container have its own LINE channel — its own identity, its own credentials, its own conversation memory — routed through the single multiplexed gateway process the container already runs, without spinning up a second full Hermes process per agent (ruled out on memory grounds in `07`).

## Reference — confirmed Hermes internals and upstream landscape (read before touching source)

**Internals** (full detail and line citations in `08`; summarized here):

- `plugins/platforms/line/adapter.py` (current tag, patches applied): `_handle_webhook` at L1117, route registration in `setup()` at L1042-1070 (`self._app.router.add_post(self.webhook_path, self._handle_webhook)`, `self.webhook_path = extra.get("webhook_path", DEFAULT_WEBHOOK_PATH)` at L881, `DEFAULT_WEBHOOK_PATH = "/line/webhook"` at L121), `_handle_message_event`'s `source_obj = self.build_source(...)` call (~L1335 per `08`).
- `gateway/platforms/base.py::build_source()` returns a `SessionSource` (`gateway/session.py`) with a mutable `.profile` field. Everything downstream that decides which profile's config/skills/memory/session a turn uses reads that one field — it doesn't care how it got set. This is the mechanism the whole patch design in `08` leans on.
- `gateway/pairing.py::PairingStore(profile=...)` — accepts an optional profile kwarg for per-profile approved-user storage; already used generically by the multiplexer for polling-platform secondary profiles.
- `SecondaryPortBindingConfigError` (`gateway/run.py` ~L9385-9420) fires only when a *secondary profile's own* `config.yaml` enables a port-binding platform. Our design (LINE channels declared once, on the default profile, each carrying its own `profile:` field) never trips this — no secondary profile's `config.yaml` ever mentions `line:` at all.

**Upstream issue tracker** (new research for this plan, 2026-08-01 — the exact multi-channel-per-port-binding-platform gap has already been raised and rejected once):

- **[#68172](https://github.com/NousResearch/hermes-agent/issues/68172) — "Config-driven channel/team-ID → profile routing (generic, cross-platform incl. port-bound platforms like Teams)."** This names our exact problem class for port-binding platforms: *"Those platforms have no path to per-tenant profile routing today without spinning up a fully separate bot registration per profile."* **Closed as not-planned / duplicate**, labeled `sweeper:implemented-on-main`. This is worth treating with real skepticism, not as "already solved": the proposed schema (`profile_routing: {teams: {"19:abc@thread.tacv2": project-alpha}}`) routes by a **tenant/team ID embedded in the payload of an already-shared credential** — the same shape as `profile_routes` (`gateway/config.py`, confirmed in `07`/`08`), which is the *shared-token* routing mechanism, not per-credential routing. LINE has no equivalent embedded tenant ID and no shared credential to route from — each channel *is* a separate credential. If "implemented on main" means `profile_routes`, the closure looks like a mis-triage for LINE's actual shape, and is exactly the kind of thing worth pointing out plainly if we file our own issue (Phase 8).
- **[#57871](https://github.com/NousResearch/hermes-agent/issues/57871) / [#57872](https://github.com/NousResearch/hermes-agent/issues/57872)** — shared-token chat/topic routing for multiplexed profiles. Same shared-credential shape as `profile_routes`; not applicable to LINE's per-channel-credential model, cited here only so a future session doesn't rediscover them and think they're the fix.
- **[#50051](https://github.com/NousResearch/hermes-agent/issues/50051) — "one-gateway-multi-profile multiplexer" bug report, opened 2026-06-21. CONFIRMED REAL on this tag, 2026-08-02, via a live production provisioning run (not a clean throwaway-profile test — see the note this supersedes below).** Reports two bugs: (A) `hermes config set gateway.multiplex_profiles true` writes a nested key `load_gateway_config()` allegedly ignores — still not independently re-verified, orthogonal to what we hit. (B) Env vars leaking across profile boundaries via `os.environ`, contradicting the documented "credentials never shared across profiles" guarantee — **this half is real**, though the trigger and blast radius are broader than the issue's own `API_SERVER_ENABLED` repro: `gateway/config.py`'s registry-driven platform-enablement loop calls each plugin's `env_enablement_fn`/`is_connected`, and LINE's (and most built-ins') implementation reads `os.getenv(...)` directly rather than the scoped `get_secret()` path `_profile_runtime_scope` actually protects — so *any* platform's credential env vars loaded into the default profile's process environment leak into every secondary profile's enablement check, not just `API_SERVER_ENABLED`. Confirmed both for LINE (`SecondaryPortBindingConfigError`, skips the whole profile) and Telegram (`✗ telegram failed to connect (profile: ...)`, degrades to a failed-connection warning since it's not port-binding). Fix that actually works, confirmed live: an explicit `platforms: <platform>: enabled: false` in the *secondary* profile's own `config.yaml` for every platform the default profile has configured — `gateway/config.py` checks for an explicit `false` before ever consulting the leaky env-based detection, so this short-circuits rather than races it. Full writeup: `HISTORICAL-GOTCHAS.md`, "Upstream #50051's env leak is real...". `ADDING-A-CLIENT-AGENT.md`'s Step 2 now leads with this fix.
- **[PR #60589](https://github.com/NousResearch/hermes-agent/pull/60589)** — adds a `GATEWAY_MULTIPLEX_PROFILES` env-var override (matches the `_env_multiplex_profiles_override()` function already found in our `gateway/config.py` reading during `07`). Confirms upstream is actively iterating on this exact feature area — re-run `upgrade-preflight.sh` discipline applies here even between our own version bumps if we start tracking multiplexing-specific upstream changes closely.

**Net read:** multiplexing is real, active upstream development, but genuinely young — an open, disputed-status bug about secondary profiles crash-looping the whole gateway, and a closed-as-duplicate issue that (on our own reading) doesn't actually cover LINE's shape, are both signs this corner of Hermes hasn't been hardened by many production users yet. Build the empirical safety net in Phase 0 before trusting it under real client traffic.

## Phase 2 — Patch `plugins/platforms/line/adapter.py` (thin call-outs) ✅ done (2026-08-01)

**Turned out less thin than "call-outs" implied, for one specific reason worth flagging to any future reader before they re-derive it:** `BasePlatformAdapter.handle_message()` is documented upstream as returning quickly by spawning a background task for the agent turn. That means `send()`/`_send_text_chunks()`/`send_image_file()`/`send_voice()`/`send_video()`/`_send_messages()`/`send_typing()`/`_keep_typing()` are **not** reliably called from within the inbound webhook request's contextvar scope — a plain `self._client` property resolving via `line_multiplex.current()` would silently break (or worse, silently use the wrong channel if some other request happened to be "current" on that worker at the time) every outbound reply on a multi-channel deployment. Fixed with `ChannelRegistry.channel_for_chat()` — a `chat_id -> channel` map recorded in `_dispatch_event` at inbound-dispatch time, read by a new `_channel_for_send(chat_id)` helper at send time, with a fallback to `line_multiplex.current()` and then (only when there is exactly one configured channel, i.e. every deployment live today) to the default channel — that last fallback is also what keeps `adapter._client = mock`-style test fixtures (see Phase 3) working unchanged. Every send-path method above was rewritten to resolve its channel this way instead of reading `self._client`. Safe for the *inbound* path only: `_client`/`allow_all`/`allowed_users`/`allowed_groups`/`allowed_rooms`/`_dm_policy` stay as contextvar-backed properties, used by `_dispatch_event` and everything it calls synchronously (mention gate, invite redemption, postback handling, media download).

**Second deviation from the sketch**: `channel_access_token`/`channel_secret` were not kept as internally-read scalar attributes at all (every internal read site now resolves the concrete channel object directly) — but they *were* added back as read-only properties purely for backward compatibility, because upstream's own `TestAdapterInit` in `tests/gateway/test_line_plugin.py` reads `adapter.channel_access_token` directly. Same story for `_client`'s setter (`adapter._client = mock` now assigns to the default channel).


**Design revision from `08`:** `08` sketched routes as `/p/{profile}/line/webhook`, mirroring the URL convention upstream's `webhook`/`api_server` platforms use for their shared listener. **Don't do that here.** That convention exists for Hermes' *shared, all-platforms* listener — LINE has never participated in that; it's always bound its own dedicated port (`LINE_PORT`) behind our own `caddy/Caddyfile`'s `handle /line/* { reverse_proxy 127.0.0.1:{$LINE_PORT:8646} }` rule, confirmed live in this plan's research (Caddyfile read directly). A route at `/p/coder/line/webhook` would **not** match `/line/*` and would silently fall through to Caddy's dashboard catch-all instead of the LINE backend — a real, easy-to-miss bug if built to the `08` sketch verbatim. Use **`/line/p/{profile}/webhook`** instead — stays under the existing `/line/*` Caddy rule, **zero `caddy/Caddyfile` changes needed**, and is arguably more correct for this codebase's actual architecture (LINE's own dedicated-port pattern) than borrowing the shared-listener convention. `08`'s reasoning about *why* per-profile routes work (the multiplexer's generic `source.profile` mechanism) is unaffected by this — only the literal path string changes.

- [x] Properties delegating to `line_multiplex.current()` (falling back to `self._channels.default()` outside any request context, matching what every one of these meant pre-patch): `channel_access_token`, `channel_secret`, `allowed_users`, `allowed_groups`, `allowed_rooms`, `allow_all`, `_dm_policy`, `_client`. **Revision from the sketch**: this covers `_dispatch_event` and everything it calls synchronously unchanged, as predicted — but NOT `send()` and the other outbound methods, which needed their own explicit resolution (see the callout above this checklist).

- [x] `_dispatch_event`: added the chat_id-remembering step (`self._channels.remember_chat(...)`) and switched the self-echo filter to the current channel's own `bot_user_id` — both new, not anticipated as separate items in the original sketch but necessary for the outbound-resolution design above.

## Phase 7 — Deploy

Staged, not all-at-once, given this is the first time this container runs more than one LINE channel:

- [ ] **Stage 1 — ship with the existing single default channel only**, no `channels` extra configured yet. This proves the patch is a true no-op for the current live client before any second channel exists. Confirm via the existing Phase 4 LINE round-trip checks from `UPGRADING.md` Phase 4 item 5 (already-approved DM gets a reply, group mention-gating unchanged) — this patch touching `__init__`/routing is exactly the kind of change that could silently break DM pairing or mention gating if the property conversion has a subtle bug, so re-run those checks even though this isn't a version bump.
- [ ] **Stage 2 — configure one real second channel** (a genuine throwaway/test LINE channel, not a second production client's channel, for this first live validation) and confirm: its own webhook URL (`https://<host>/line/p/<test-profile>/webhook`) registered in *that* channel's LINE Developers Console entry, a message on it reaches the correspondingly-profiled agent with a distinct reply and distinct memory from the default channel, and a message on the *original* default channel still behaves unchanged (regression check under real concurrent traffic, not just sequential test cases).
- [ ] **Stage 3 — first real client second-channel rollout**, only after Stage 2 has run clean for some period (decide how long before starting Stage 2, not after).

### Rollback

Revert `Dockerfile`'s patch-apply step to the two-patch chain (or the whole tag, if something upstream also moved) and redeploy — cheap, same reasoning as every other rollback in `UPGRADING.md`: the image carries no state, `/opt/data` is untouched by a deploy. If Stage 2/3 surfaces a cross-channel isolation failure (the one genuinely severe failure mode here — one client's data reaching another's agent), roll back immediately and treat it as a security incident, not an ordinary bug, regardless of how it's caught.
