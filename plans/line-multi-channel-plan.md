## Goal

Let each client agent within one business's container have its own LINE channel — its own identity, its own credentials, its own conversation memory — routed through the single multiplexed gateway process the container already runs, without spinning up a second full Hermes process per agent (ruled out on memory grounds in `07`).

## Reference — confirmed Hermes internals and upstream landscape (read before touching source)

**Internals** (full detail and line citations in `08`; summarized here):

- `plugins/platforms/line/adapter.py` (current tag, patches applied): `_handle_webhook` at L1117, route registration in `setup()` at L1042-1070 (`self._app.router.add_post(self.webhook_path, self._handle_webhook)`, `self.webhook_path = extra.get("webhook_path", DEFAULT_WEBHOOK_PATH)` at L881, `DEFAULT_WEBHOOK_PATH = "/line/webhook"` at L121), `_handle_message_event`'s `source_obj = self.build_source(...)` call (~L1335 per `08`).
- `gateway/platforms/base.py::build_source()` returns a `SessionSource` (`gateway/session.py`) with a mutable `.profile` field. Everything downstream that decides which profile's config/skills/memory/session a turn uses reads that one field — it doesn't care how it got set. This is the mechanism the whole patch design in `08` leans on.
- `gateway/pairing.py::PairingStore(profile=...)` — accepts an optional profile kwarg for per-profile approved-user storage; already used generically by the multiplexer for polling-platform secondary profiles.
- `SecondaryPortBindingConfigError` (`gateway/run.py` ~L9385-9420) fires only when a *secondary profile's own* `config.yaml` enables a port-binding platform. Our design (LINE channels declared once, on the default profile, each carrying its own `profile:` field) never trips this — no secondary profile's `config.yaml` ever mentions `line:` at all.

**Upstream issue tracker** (new research for this plan, 2026-08-01 — the exact multi-channel-per-port-binding-platform gap has already been raised and rejected once):

- **[#68172](https://github.com/NousResearch/hermes-agent/issues/68172) — "Config-driven channel/team-ID → profile routing (generic, cross-platform incl. port-bound platforms like Teams)."** This names our exact problem class for port-binding platforms: *"Those platforms have no path to per-tenant profile routing today without spinning up a fully separate bot registration per profile."* **Closed as not-planned / duplicate**, labeled `sweeper:implemented-on-main`. This is worth treating with real skepticism, not as "already solved": the proposed schema (`profile_routing: {teams: {"19:abc@thread.tacv2": project-alpha}}`) routes by a **tenant/team ID embedded in the payload of an already-shared credential** — the same shape as `profile_routes` (`gateway/config.py`, confirmed in `07`/`08`), which is the *shared-token* routing mechanism, not per-credential routing. LINE has no equivalent embedded tenant ID and no shared credential to route from — each channel *is* a separate credential. If "implemented on main" means `profile_routes`, the closure looks like a mis-triage for LINE's actual shape, and is exactly the kind of thing worth pointing out plainly if we file our own issue (Phase 8).
- **[#57871](https://github.com/NousResearch/hermes-agent/issues/57871) / [#57872](https://github.com/NousResearch/hermes-agent/issues/57872)** — shared-token chat/topic routing for multiplexed profiles. Same shared-credential shape as `profile_routes`; not applicable to LINE's per-channel-credential model, cited here only so a future session doesn't rediscover them and think they're the fix.
- **[#50051](https://github.com/NousResearch/hermes-agent/issues/50051) — "one-gateway-multi-profile multiplexer" bug report, opened 2026-06-21.** Reports two bugs: (A) `hermes config set gateway.multiplex_profiles true` writes a nested key `load_gateway_config()` allegedly ignores (our own reading of `gateway/config.py` during `07`'s research found explicit nested-key handling with a comment referencing exactly this CLI command, so this looks fixed on our tag — but wasn't independently re-verified against the issue's specific repro). (B) **`API_SERVER_ENABLED=true` on the default profile leaks into secondary profiles via shared `os.environ`, causing every secondary profile to spuriously resolve as port-binding-enabled and crash-loop the whole gateway (`MultiplexConfigError`), not just skip that one profile.** Fetched twice during this plan's research with **conflicting status signals** (one fetch read "open, unresolved, verified against commit `02a3288`"; a second read the issue as closed with no fix reference) — GitHub's rendered state wasn't reliably scraped either time, so **treat this as unverified, not resolved, until Phase 0 proves it empirically on our own tag.** `API_SERVER_ENABLED` itself isn't set in our `.env` today, so the *specific* trigger in the bug report doesn't currently fire for us — but the underlying claim (env vars leaking across profile boundaries via `os.environ`, contradicting the documented "credentials never shared across profiles" guarantee) is exactly the kind of thing that would quietly break this whole plan if true for *any* LINE-related env var, not just `API_SERVER_ENABLED`. This is why Phase 0 below tests basic multiplexing health with a throwaway non-LINE profile **before** any LINE-specific code gets written — cheap to test, expensive to discover after the LINE patch is already built on top of an assumption that turned out false.
- **[PR #60589](https://github.com/NousResearch/hermes-agent/pull/60589)** — adds a `GATEWAY_MULTIPLEX_PROFILES` env-var override (matches the `_env_multiplex_profiles_override()` function already found in our `gateway/config.py` reading during `07`). Confirms upstream is actively iterating on this exact feature area — re-run `upgrade-preflight.sh` discipline applies here even between our own version bumps if we start tracking multiplexing-specific upstream changes closely.

**Net read:** multiplexing is real, active upstream development, but genuinely young — an open, disputed-status bug about secondary profiles crash-looping the whole gateway, and a closed-as-duplicate issue that (on our own reading) doesn't actually cover LINE's shape, are both signs this corner of Hermes hasn't been hardened by many production users yet. Build the empirical safety net in Phase 0 before trusting it under real client traffic.

## Phase 1 — Build the testable module

All substantive logic lives in a new sibling module, `modules/line/line_multiplex.py`, `COPY`'d into the image next to the existing `modules/line/render_mention.py` — unit-testable with no upstream clone, following `line-group-mention.patch`'s own proven shape (see `patches/README.md`'s rationale for that split, and `08`'s "Architecture" section for why this patch follows it too).

- [ ] `LineChannel` dataclass: `profile`, `channel_secret`, `channel_access_token`, `allowed_users`, `allowed_groups`, `allowed_rooms`, `allow_all`, `dm_policy`, `home_channel`, `client` (its own `_LineClient` instance — imported from the adapter module at call time to avoid a circular import; confirm this before assuming it's trivial, since `_LineClient` currently lives in `adapter.py`, not a shared module).
- [ ] `ChannelRegistry`: built from `extra.get("channels")` (a list) plus the adapter's own top-level `LINE_CHANNEL_SECRET`/`LINE_CHANNEL_ACCESS_TOKEN`/etc. registered as one more entry (the default channel) — **every existing single-channel deployment must produce a registry with exactly one entry and behave byte-identical to today**, since this has to ship to already-live client instances with zero config changes. Methods: `by_profile(name)`, `by_webhook_path(path)`.
- [ ] `contextvars.ContextVar[LineChannel]` for "current request's channel," plus `set_current()`/`current()` helpers. **Use `contextvars`, not a plain instance attribute** — the aiohttp server handles concurrent requests from *different channels* interleaved on one event loop, and `asyncio.create_task()` (used for the typing-indicator ping in `_handle_message_event`) copies the context automatically, which a manually mutated-and-restored attribute would not get safely. This is the one correctness property in the whole design that has to be right, not just convenient — see `08` for the exact race it avoids.
- [ ] `tests/test_line_multiplex.py` (mirrors `tests/test_render_mention.py`'s standalone-module-load pattern, no upstream clone needed): registry construction from a `channels` list, registry construction from zero-`channels` extra (backward-compat single-channel path), `by_profile`/`by_webhook_path` lookup, contextvar isolation between two "concurrent" simulated requests (set channel A, yield, confirm channel B's context doesn't see it — the specific race this design exists to prevent).

## Phase 2 — Patch `plugins/platforms/line/adapter.py` (thin call-outs)

**Design revision from `08`:** `08` sketched routes as `/p/{profile}/line/webhook`, mirroring the URL convention upstream's `webhook`/`api_server` platforms use for their shared listener. **Don't do that here.** That convention exists for Hermes' *shared, all-platforms* listener — LINE has never participated in that; it's always bound its own dedicated port (`LINE_PORT`) behind our own `caddy/Caddyfile`'s `handle /line/* { reverse_proxy 127.0.0.1:{$LINE_PORT:8646} }` rule, confirmed live in this plan's research (Caddyfile read directly). A route at `/p/coder/line/webhook` would **not** match `/line/*` and would silently fall through to Caddy's dashboard catch-all instead of the LINE backend — a real, easy-to-miss bug if built to the `08` sketch verbatim. Use **`/line/p/{profile}/webhook`** instead — stays under the existing `/line/*` Caddy rule, **zero `caddy/Caddyfile` changes needed**, and is arguably more correct for this codebase's actual architecture (LINE's own dedicated-port pattern) than borrowing the shared-listener convention. `08`'s reasoning about *why* per-profile routes work (the multiplexer's generic `source.profile` mechanism) is unaffected by this — only the literal path string changes.

- [ ] `__init__` (patch lands after both existing patches' `__init__` additions — see "Interaction with existing patches" below): parse `extra.get("channels")` into the module's `ChannelRegistry`; **remove** the direct `self.channel_secret = ...` / `self.channel_access_token = ...` assignments and `self._dm_policy = ...` (added by `line-dm-pairing.patch`) in favor of the properties below.
- [ ] Convert to properties delegating to `line_multiplex.current()`: `channel_secret`, `channel_access_token`, `allowed_users`, `allowed_groups`, `allowed_rooms`, `allow_all`, `_dm_policy`. **This is the reason `_dispatch_event`, `_handle_message_event`, `_handle_postback_event`, `_try_handle_invite_redemption`, and `send()` need no further changes** — they already reference these names; they now just resolve per-request instead of per-process.
- [ ] `_client` property — same delegation, replacing the single instance-level `_LineClient`. Confirm every existing `self._client` reference (reply/push calls, `.loading()` typing indicator, `get_profile()` in the invite-redemption path) still resolves correctly through the property — these are call sites, not definitions, so they shouldn't need edits, but verify in Phase 3's tests rather than assuming.
- [ ] `setup()` (~L1042-1070): replace the single `self._app.router.add_post(self.webhook_path, self._handle_webhook)` with a loop over the registry — the default channel keeps the existing unprefixed `/line/webhook` (zero change for every live single-channel instance's already-configured LINE console callback URL), every other channel gets `/line/p/{profile}/webhook`.
- [ ] `_handle_webhook` (~L1117): resolve which channel this request's route matched (`request.match_info.get("profile")`, defaulting to the default channel for the unprefixed route), call `line_multiplex.set_current(channel)` for the duration of the request (a `Context.run()`/token pattern, not a bare global set), verify the signature against *that* channel's secret, then proceed as today. The whole batch loop (`for event in events: await self._dispatch_event(event)`) stays inside this one context-set, since a single webhook POST is always one channel's events.
- [ ] `_handle_message_event` / `_handle_postback_event`: **one line added** after each existing `source_obj = self.build_source(...)` call: `source_obj.profile = line_multiplex.current().profile`. Per the Reference section above, this one field is the entire mechanism that makes the agent turn resolve to the right profile's config/skills/memory — nothing else in either method needs to change.
- [ ] `plugin.yaml`: document `channels` as a `platforms.line.extra.channels` structured-config key — **not** representable in `.env` (it's a list), which is a first for this repo's LINE surface where every other knob today is env-var driven. Flag this explicitly in the doc text so it isn't assumed to work like `LINE_ALLOWED_USERS` does.

### Interaction with the two patches already in `patches/`

Per `08`'s finding, `__init__` is the collision point: `line-dm-pairing.patch` adds `self._dm_policy`/`self._invites`, `line-group-mention.patch` adds `self._mention_gate`. This patch's `__init__` hunk has to be generated against a tree with **both already applied**, and specifically *replaces* (not adds near) the `self._dm_policy = ...` line. Apply/generate order: **dm-pairing → group-mention → multi-channel**, matching `patches/CLAUDE.md`'s existing ordering rule extended to three. Expect this to require re-diffing `__init__` as a whole rather than a clean independent hunk stack — call this out explicitly when regenerating, don't assume `git apply` will silently sort it out.

### Rollback

Revert `Dockerfile`'s patch-apply step to the two-patch chain (or the whole tag, if something upstream also moved) and redeploy — cheap, same reasoning as every other rollback in `UPGRADING.md`: the image carries no state, `/opt/data` is untouched by a deploy. If Stage 2/3 surfaces a cross-channel isolation failure (the one genuinely severe failure mode here — one client's data reaching another's agent), roll back immediately and treat it as a security incident, not an ordinary bug, regardless of how it's caught.
