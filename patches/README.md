# patches/

Source-level patches applied to the pinned `HERMES_IMAGE` at Docker build
time (see the `Dockerfile`'s `git apply` step). This is a stopgap for
functionality that hasn't merged upstream yet — see
`plans/line-dm-pairing-plan.md` for the project this directory currently
exists for. Once a patch's upstream PR merges and `HERMES_IMAGE` is
bumped to a release that includes it, delete the patch file and the
`Dockerfile` step that applies it.

## Why a patch file instead of forking the image

The upstream image (`docker.io/nousresearch/hermes-agent`) ships plain,
uncompiled `.py` source at `/opt/hermes/...` — not a `.git` checkout, but
`git apply` is present in the base image (`patch` is not). That makes it
possible to apply a small diff at build time without maintaining a full
forked image build/push pipeline. Confirmed against the actual pulled
image, not assumed — see the `git show` of the commit that added this
directory for the verification transcript if needed.

## Applying (already wired up)

The `Dockerfile` does, right after `FROM ${HERMES_IMAGE}`:

```dockerfile
COPY modules/line/render_mention.py /opt/hermes/plugins/platforms/line/render_mention.py
COPY modules/line/line_multiplex.py /opt/hermes/plugins/platforms/line/line_multiplex.py
COPY patches/line-dm-pairing.patch /tmp/line-dm-pairing.patch
COPY patches/line-group-mention.patch /tmp/line-group-mention.patch
COPY patches/line-multi-channel.patch /tmp/line-multi-channel.patch
RUN cd /opt/hermes && git apply -p1 --verbose /tmp/line-dm-pairing.patch \
 && git apply -p1 --verbose /tmp/line-group-mention.patch \
 && git apply -p1 --verbose /tmp/line-multi-channel.patch \
 && rm /tmp/line-dm-pairing.patch /tmp/line-group-mention.patch /tmp/line-multi-channel.patch
```

`-p1` matches the strip level of a patch generated by `git diff`/`git
format-patch` from a repo root (i.e. `a/plugins/...` / `b/plugins/...`
prefixes) — which is exactly how these patches are generated below.

**Order is load-bearing.** `line-group-mention.patch` is generated against a
tree that *already* has `line-dm-pairing.patch` applied, and
`line-multi-channel.patch` against a tree with *both* already applied — all
three touch overlapping regions of `adapter.py`/`plugin.yaml` (`__init__`,
`_handle_message_event`, `plugin.yaml`'s `optional_env`), so each one's
context lines include the prior ones' additions. Applied out of order, or any
one applied standalone against pristine upstream, fails with "patch does not
apply" (verified for all three, including generating `line-multi-channel.patch`
against the wrong baseline the first time — see its own worked-example note
below). Keep them in this order, and generate them in this order.

**Not everything lives in a patch.** The group mention-gate *logic* ships as
`modules/line/render_mention.py`, and the multi-channel routing/credential
logic as `modules/line/line_multiplex.py`, both `COPY`'d into the upstream
LINE plugin's own package directory. Nothing patches either file — they're
new sibling modules, importable as `plugins.platforms.line.render_mention`
and `plugins.platforms.line.line_multiplex` because that directory is
a real package on Hermes' editable install. `line-group-mention.patch` and
`line-multi-channel.patch` are then each just a thin layer of call-outs (the
former ~20 lines: one import, one attribute, one gate block, one postback
branch, two `plugin.yaml` entries; the latter covers `__init__`'s channel
registry, `connect()`/`disconnect()`'s per-channel loop, `_handle_webhook`'s
channel resolution, and the `source.profile` stamp — see
`line_multiplex.py`'s own docstring for the split rationale). That split
exists so upstream drift can only break the thin hunk — loudly, at build
time — and so the substantive logic is unit-testable in this repo with no
upstream clone at all (`tests/test_render_mention.py`,
`tests/test_line_multiplex.py`, `python3 -m pytest tests/`).

The adapter imports the module unguarded, on purpose. A missing module then
fails at container start rather than silently leaving groups ungated — a
`try/except ImportError` here would convert a loud, pre-deploy build error into
a silent fail-open in a client's group chat. `scripts/smoke-test.sh` asserts
the real import before any deploy.

## Regenerating a patch after bumping `HERMES_IMAGE`

**A patch generated against one upstream tag is not guaranteed to apply
against another.** `git apply` matches on context lines, not just line
numbers — if upstream touched the same file, the old patch can fail
loudly (it does not silently mis-apply) with a "patch does not apply"
error at `docker build` time.

**First, find out whether you need to.** `./scripts/upgrade-preflight.sh
<new-tag>` (see `UPGRADING.md` Phase 1) diffs the two files these patches
touch between the pinned tag and the candidate, in about a minute, without a
clone or a `docker pull`. It replaces steps 1-2 below for the common case: if
it reports `plugins/platforms/line/adapter.py` and `plugin.yaml` unchanged,
the existing patches apply as-is and there is nothing to regenerate. If it
reports drift, confirm with the `git apply -p1 --check` one-liner in step 5
before assuming the worst — `git apply` matches context and tolerates line
offsets, so upstream can touch a file without breaking our hunks.

Only when that check actually fails, regenerate every patch in this
directory against the new tag before deploying:

```bash
# 1. Clone the exact new tag (shallow, fast) — do NOT edit the running
#    container's files, this is a throwaway clone purely to get a clean
#    "before" tree at the new tag.
git clone --branch <new-tag> --depth 1 \
  https://github.com/NousResearch/hermes-agent.git /tmp/hermes-agent-src
cd /tmp/hermes-agent-src

# 2. Sanity-check: confirm this clone's source is byte-identical to what
#    actually ships in the pulled image at that tag, before trusting it
#    as the diff base. (The public tag and the image should always
#    match, but this check is cheap and catches a bad tag/build drift
#    early instead of shipping a patch generated against the wrong tree.)
docker pull docker.io/nousresearch/hermes-agent:<new-tag>
docker create --name hermes-verify docker.io/nousresearch/hermes-agent:<new-tag>
docker cp hermes-verify:/opt/hermes/plugins/platforms/line/adapter.py /tmp/adapter.py.image
docker rm hermes-verify
diff -u plugins/platforms/line/adapter.py /tmp/adapter.py.image && echo IDENTICAL

# 3. Re-apply the intent of the old patch by hand (the actual Phase 2
#    diff — dm_policy attribute, enforces_own_access_policy property,
#    _is_dm_intake_allowed, the _dispatch_event gate rewrite — since a
#    conflicting old patch can't just be re-applied mechanically if
#    upstream shifted the surrounding code).

# 4. Regenerate the patch file(s):
git diff -- plugins/platforms/line/adapter.py plugins/platforms/line/plugin.yaml \
  > patches/line-dm-pairing.patch

# 5. Validate the new patch applies cleanly against the *actual* new
#    image (not just the clone) before committing it — this is the same
#    check the Dockerfile build will do:
docker run --rm -v "$(pwd)/patches/line-dm-pairing.patch:/tmp/p.patch:ro" \
  --entrypoint sh docker.io/nousresearch/hermes-agent:<new-tag> -c \
  'cd /opt/hermes && git apply -p1 --check /tmp/p.patch && echo CHECK OK'

# 6. Rebuild and run the full smoke test:
./scripts/smoke-test.sh
```

## Files

- `line-dm-pairing.patch` — applied to the deployed image (adapter +
  plugin manifest only). Covers **both** Phase 2 (the `dm_policy` fix —
  see `plans/line-dm-pairing-plan.md` Phase 2) and Phase 6c (the
  manager-initiated one-off QR join invite — `LineInviteStore`,
  `_LineClient.get_profile`, the invite-redemption branch in
  `_dispatch_event`, and `LINE_BASIC_ID` in `plugin.yaml`). Both land in
  the same file because they touch the same two files; there's no
  Phase-numbered split on disk.
- `line-dm-pairing.tests.patch` — the accompanying test coverage
  (`tests/gateway/test_line_plugin.py`), covering both phases above.
  **Not applied by the Dockerfile** — the upstream image doesn't ship a
  `tests/` directory at all, so this file exists only to (a) hand to Nous
  alongside a Phase 2 upstream PR (Phase 6c is deliberately **not**
  submitted upstream — see the plan's Phase 5 checklist), and (b) let a
  future patch-regeneration pass re-verify against the same test coverage
  locally. Apply it against a local clone of `hermes-agent` if you need
  to re-run the tests, not against the Docker image.
- `line-group-mention.patch` — group/multi-person mention gating. Applied to
  the deployed image **after** `line-dm-pairing.patch` (see "Order is
  load-bearing" above). Deliberately thin: an import, the `MentionGate`
  attribute, the gate block in `_handle_message_event` (placed ahead of the
  reply-token stash so a dropped message never banks a single-use token), a
  `set_line_mode` branch in `_handle_postback_event`, and two `plugin.yaml`
  entries (`LINE_REQUIRE_MENTION`, `LINE_MENTION_FOLLOWUP_SECONDS`). All the
  logic it calls lives in `modules/line/render_mention.py`.

  This one *is* a reasonable upstream PR on its own: LINE is the only major
  adapter in Hermes without a `require_mention` switch (Discord, Slack,
  Telegram, Mattermost, WhatsApp, Matrix, Feishu, DingTalk and Photon all
  have one). Upstreaming it would mean folding `render_mention.py` in as a
  normal module rather than a `COPY`.
- `line-multi-channel.patch` — lets the one `LineAdapter` instance the
  default profile runs serve several distinct LINE Developers Console
  channels (own credentials, allowlists, `dm_policy` each), configured via
  a new `platforms.line.extra.channels` structured-config key. Applied
  **after** both patches above (see "Order is load-bearing"). Works around
  `gateway.multiplex_profiles`'s inability to give a secondary profile its
  own instance of a port-binding platform like LINE
  (`SecondaryPortBindingConfigError` in `gateway/run.py`) without running a
  second full Hermes gateway process per client agent — ruled out on this
  deployment's memory budget, see `plans/line-multi-channel-plan.md` and
  `research/07-line-multi-channel-multiplexing.md`. All the routing/
  credential-resolution logic lives in `modules/line/line_multiplex.py`.

  This is a genuine new capability, not really upstream-PR shaped on its
  own the way the mention-gate patch is: it's the same category as the
  open, `needs-decision` multi-tenancy issues tracked in
  `research/02-nous-platform-risk.md` (#527, #34352), not a small missing
  switch. Worth filing an issue regardless (see the plan's Phase 8) — don't
  block on a merge.
- `line-multi-channel.tests.patch` — adapter-level integration tests for
  the above (`tests/gateway/test_line_plugin.py`), same not-applied-by-the-
  Dockerfile status as `line-dm-pairing.tests.patch`. Also carries one
  fix unrelated to multi-channel itself: a one-line pre-import
  (`import plugins.platforms.line` before the isolated-name
  `load_plugin_adapter("line")` load) that was needed to make this test
  file collectible via pytest at all once `adapter.py` gained *any*
  `from plugins.platforms.line import <sibling>` statement — a latent gap
  from `line-group-mention.patch` that had gone unexercised because no
  test patch for that one ever drove this file's collection path.
- The `line-invite` skill itself (the QR-generation side of Phase 6c)
  is **not** part of either patch file — it's a separate, unpatched
  addition living in this repo's own `skills/line-invite/`, baked into
  the image and registered via `scripts/patch-config.py` +
  `scripts/bootstrap.sh` (see the Dockerfile's `line-invite skill`
  section). Regenerating the patches above never touches it.
